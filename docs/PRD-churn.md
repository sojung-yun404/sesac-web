## 1. 배경과 목표

### 페르소나

> **음악 스트리밍 서비스 Sparkify의 그로스/CRM 마케터.**
> 매달 이탈 방어 캠페인 예산을 집행하지만, 근거는 "지난달에 이렇게 했으니까"에 가깝다.
> 데이터팀이 이탈 예측 모델(GBT, F1 0.97)을 만들어줬는데, 그 결과가
> **주피터 노트북 안에만 있어서** 캠페인에 쓸 수가 없다.
> 필요한 건 모델 정확도가 아니라 **오늘 CRM 툴에 업로드할 CSV 한 장**이다.

### 이 대시보드가 답해야 할 네 가지 질문

인터뷰에서 네 가지 모두 필요하다고 확인되었다. 다만 **우선순위가 있다.**

| 순위 | 질문 | 대응 섹션 | 성격 |
|---|---|---|---|
| 1 | 지금 **누가** 이탈 위험인가 | §4 타겟 리스트 | 액션 |
| 2 | 캠페인을 **어디에** 써야 ROI가 높은가 | §5 ROI 시뮬레이터 | 의사결정 |
| 3 | **왜** 이탈하는가 | §3 원인 진단 | 인사이트 |
| 4 | 이탈률이 **어떻게** 변하고 있나 | §2 모니터링 | 감시 |

> 화면 순서는 4 → 3 → 1 → 2 (모니터링에서 이상을 감지하고 → 원인을 좁히고 →
> 대상을 뽑고 → 예산을 정하는 흐름)로 배치한다.
> 우선순위가 높은 섹션일수록 **정보 밀도를 낮추고 액션 버튼을 크게** 둔다.

### 성공 기준

| 지표 | 목표 |
|---|---|
| 대시보드 진입 → 캠페인 대상 CSV 다운로드 | 클릭 3회 이내 |
| 이탈 원인 상위 3개 파악 | 스크롤 1회 이내 |
| 초기 페이지 로드 | 2초 이내 (모바일 4G) |
| 팀 공유 | 링크 하나로 로그인 없이 열람 |

## 2. 사용자 스토리

1. 월요일 아침, **지난주 대비 이탈률이 튀었는지** 먼저 확인하고 싶다.
2. 이탈률이 올랐다면 **어느 세그먼트에서 올랐는지** 바로 좁히고 싶다.
3. 데이터팀 없이도 **"가입 30일 미만 + 위험도 상위 20%"** 같은 조건으로 대상을 뽑고 싶다.
4. 뽑은 대상을 **CSV로 받아 CRM 툴에 그대로 업로드**하고 싶다.
5. 대상마다 **어떤 메시지를 보내야 하는지** 감이 없다. 위험 유형별로 제안을 받고 싶다.
6. 상사에게 **"이 캠페인에 500만원 쓰면 얼마 벌어오나"** 를 숫자로 보고해야 한다.
7. 무료→유료 이탈(해지)과 유료→무료 강등(다운그레이드)은 **다른 문제**라 따로 보고 싶다.

## 3. 이탈(Churn) 정의

인터뷰 결정: **해지와 다운그레이드를 분리 추적한다.**

| 구분 | 정의 (원본 이벤트) | CRM 관점 |
|---|---|---|
| **Hard Churn (해지)** | `page = Cancellation Confirmation` | 계정 소멸. 복구 비용이 가장 큼 |
| **Soft Churn (다운그레이드)** | `page = Submit Downgrade` | 유료→무료. 매출은 잃되 관계는 유지 |

두 그룹에 보낼 메시지가 완전히 다르기 때문에 분리한다.
Hard Churn 예정자에게는 **잔존 유인(할인·독점 콘텐츠)**, Soft Churn 예정자에게는
**가치 재인식(내가 이번 달 들은 시간, 유료 전용 기능 사용 이력)** 이 필요하다.

> 원본 노트북은 Hard Churn만 `churn=1`로 라벨링했다. 본 대시보드는 두 라벨을
> 모두 생성하되 **모델 타겟은 Hard Churn**으로 유지해 원본과 비교 가능하게 한다.

## 5. 기능 요구사항

### F1. KPI 헤더

한 줄로 현재 상태를 요약. 각 지표는 **직전 기간 대비 변화**를 함께 표시한다.

| 지표 | 정의 |
|---|---|
| 전체 사용자 | 관측 기간 내 활동 이력이 있는 고유 사용자 |
| Hard Churn율 | 해지 사용자 / 전체 |
| Soft Churn율 | 다운그레이드 사용자 / 유료 사용자 |
| 고위험군 규모 | 위험 점수 상위 구간에 속한 잔존 사용자 수 |
| 위험 MRR | 고위험군 중 유료 사용자 × 월 구독료 |

### F2. 이탈 추이 모니터링

- 일별 신규 해지 / 다운그레이드 이중 라인 차트
- 7일 이동평균 오버레이 (일별 노이즈 제거)
- 일별 활성 사용자(DAU) 보조 축
- **기간 선택** (전체 / 최근 30일 / 최근 14일)

### F3. 이탈 원인 진단

원본 노트북의 GBT 피처 중요도 상위 3개(**가입 기간, Thumbs Down, 친구 수**)를 축으로 삼되,
"중요도" 막대만 보여주면 마케터가 액션으로 옮길 수 없다.
→ **드라이버별 구간(bucket) 이탈률 비교**로 표현한다.

| 드라이버 | 구간 | 읽는 법 |
|---|---|---|
| 가입 기간 | ~30일 / 30~60 / 60~90 / 90일~ | 언제 이탈이 몰리는가 → 온보딩 개입 시점 |
| Thumbs Down 비율 | 4분위 | 추천 품질 불만이 이탈로 이어지는가 |
| 친구 수 | 0명 / 1~5 / 6~15 / 16명~ | 소셜 그래프가 잔존에 기여하는가 |
| 세션 빈도 | 4분위 | 사용 빈도 저하가 선행지표인가 |
| 광고 노출 (무료) | 4분위 | 광고 피로가 이탈 요인인가 |

각 구간에 **이탈률 + 사용자 수**를 병기한다. 사용자 수가 적은 구간의
높은 이탈률은 신뢰할 수 없으므로 표본이 작으면 경고 표시한다.

### F4. 타겟 리스트 + CSV 내보내기 (핵심)

- **필터**: 위험도 구간 / 가입 기간 / 요금제 / 위험 유형 / 성별
- **표 컬럼**: userId / 위험점수 / 위험유형 / 요금제 / 가입일수 / 세션수 / Thumbs Down / 친구수 / 추천 액션
- 위험 점수 내림차순 기본 정렬
- **CSV 내보내기** — 현재 필터 결과 전체를 다운로드
  - 컬럼: `user_id, risk_score, risk_tier, risk_type, level, days_member, recommended_action`
  - CRM 툴(Braze/CleverTap 등)에 바로 업로드 가능한 평면 구조
- 화면 표시는 상위 100행으로 제한(렌더 성능), **CSV는 필터 전체**를 담는다

### F5. 위험 유형 분류 + 추천 액션

위험 점수만으로는 "무엇을 보낼지"를 알 수 없다. 기여도가 가장 큰 요인으로 유형을 나눈다.

배정 방식은 **위험 기여도 분해**다. 각 드라이버를 관측 지표에서 z-score로 표준화하고
모델 계수를 가중치로 곱해, 그 사용자의 위험을 가장 크게 끌어올린 요인 하나를 고른다.

> 임계값 기반 if-else를 쓰지 않는 이유: 조건 순서에 따라 유형이 갈려, 고위험 사용자가
> 먼저 걸린 유형에 쏠리고 나머지 유형에는 저위험 사용자만 남는 편향이 생긴다.
> 실제로 초기 구현에서 "콘텐츠 불만" 세그먼트의 이탈률이 기저율보다 **낮게**
> 나오는 역전이 발생했다.

| 위험 유형 | 판별 기준 | 추천 CRM 액션 |
|---|---|---|
| **온보딩 실패** | 재적 기여도 최대 & 가입 30일 미만 | 첫 플레이리스트 만들기 가이드, D+3/D+7 온보딩 저니 |
| **정착 실패** | 재적 기여도 최대 & 가입 30~90일 | 습관 형성 유도, 주간 개인화 믹스, 청취 리마인더 |
| **콘텐츠 불만** | Thumbs Down 비율 기여도 최대 | 취향 재설정 요청, 큐레이션 재추천, 신규 장르 제안 |
| **고립형** | 친구·플레이리스트 부족 기여도 최대 | 친구 초대 인센티브, 공유 플레이리스트 유도 |
| **저활성** | 세션 빈도 저하 기여도 최대 | 리인게이지먼트 푸시, 개인화 위클리 믹스 |
| **광고 피로** | 무료 & 광고 노출 기여도 최대 | 유료 체험 프로모션, 광고 없는 주말 티저 |

> 하나의 사용자에게 **유형은 하나만** 배정한다. 마케터가 세그먼트를 겹치지 않게
> 운영할 수 있어야 하기 때문이다.
>
> **재적 기간만 절대 경계를 함께 둔다.** 상대 z-score만 쓰면 가입 90일차 사용자도
> "재적이 짧은 편"으로 분류되어 정착한 사용자에게 온보딩 메시지가 나간다.
> 순위는 기여도로 매기되, 30일 미만은 온보딩 · 30~90일은 정착 · 90일 이상은
> 재적 기간을 유형 후보에서 제외한다.

### F6. 캠페인 ROI 시뮬레이터

상사 보고용 숫자를 만드는 화면. 입력 3개, 출력 4개로 단순하게 유지한다.

**입력**
- 타겟 범위: 위험도 상위 N% (슬라이더)
- 1인당 캠페인 비용 (쿠폰·할인 원가)
- 예상 방어율 (캠페인으로 이탈을 막을 확률)

**출력**
- 타겟 인원 / 총 캠페인 비용
- 예상 방어 인원 (= 타겟 중 실제 이탈 예정자 × 방어율)
- 구한 매출 (= 방어 인원 × 월 구독료 × 유지 개월 가정)
- **순이익 / ROI(%)** — 손익분기 방어율을 함께 표시

**기본 가정** (화면에서 조정 가능하게 노출)

| 항목 | 기본값 | 근거 |
|---|---|---|
| 월 구독료 | 10,900원 | 국내 음원 스트리밍 표준가 |
| 방어 후 평균 유지 기간 | 6개월 | 보수적 가정 |
| 예상 방어율 | 25% | 리텐션 캠페인 업계 통상 범위(15~35%) 중앙값 |

> ROI가 좋아 보이도록 기본값을 낙관적으로 잡지 않는다.
> 이 화면의 목적은 설득이 아니라 **손익분기점을 아는 것**이다.

## 6. 데이터

### 소스와 생성 방식

인터뷰 결정: **합성 데이터 5,000명 규모.**

원본 mini 데이터셋은 고유 사용자가 **225명(해지 52명)** 뿐이라, 세그먼트를 5개로만 나눠도
칸당 10명 내외가 되어 이탈률이 표본 노이즈에 압도된다. 대시보드의 목적이
"세그먼트별 비교"인 이상 이 규모로는 기능이 성립하지 않는다.

따라서 **원본의 통계적 구조를 보존한 채 규모만 확장**한 합성 데이터를 생성한다.

**보존하는 원본 특성**

| 특성 | 원본 값 | 출처 |
|---|---|---|
| Hard Churn율 | 23.1% (52/225) | 노트북 EDA |
| 관측 기간 | 2018-10-01 ~ 2018-12-03 (64일) | 노트북 In[15] |
| 가입일 범위 | 2018-03-18 ~ 2018-11-26 | `registration` min/max |
| 유료 비중 | 소수 (대부분 free) | 노트북 In[24] |
| 곡 길이 평균 | 249초 (σ 99) | `length` describe |
| 이탈자 특성 | 재적 짧음 · 청취량 적음 · Thumbs Up/친구/플레이리스트 적음 | 노트북 EDA |
| 드라이버 중요도 | 가입기간 > Thumbs Down > 친구 수 | GBT feature importance |
| 성별 패턴 | 남성 해지↑, 여성 다운그레이드↑ | 노트북 In[23] |

**생성 방식**: 잠재 위험도(latent propensity) 모델
1. 사용자별 기본 속성 표본 추출 (가입일, 성별, 요금제, OS, 지역)
2. 드라이버 가중합으로 잠재 위험 로짓 `z` 계산
3. `z`에 조건부로 행동 피처 생성 (위험 높음 → 참여 낮음)
4. `p = sigmoid(z)` 에서 이탈 여부 베르누이 추출 — 절편은 전체 이탈률 23.1%에 맞춰 보정
5. 예측 스코어 = `z`에 노이즈를 더한 값 (실제 모델의 불완전성 재현)

> **모델 성능에 대한 주의.** 원본 노트북의 GBT는 F1 0.97을 기록했지만, 이는
> **누수(leakage)를 의심할 만한 수치**다. 이탈자는 해지 시점에 로그가 끊기므로
> `days_member`·`num_sessions` 같은 피처가 관측 기간 전체를 쓰는 잔존자와
> 구조적으로 다르게 계산된다. 즉 모델이 "이탈 징후"가 아니라 "이탈했다는 사실"을
> 학습했을 가능성이 있다.
> 본 대시보드는 **예측 시점을 고정**하고 F1 0.80 내외의 현실적인 성능을 가정한다.
> 실제 성능은 생성 스크립트가 계산해 `model` 블록에 기록한다.

### 재현성

- 난수 시드 고정 (`SEED = 42`) → 스크립트를 다시 돌려도 동일한 데이터
- Python 표준 라이브러리만 사용 (기존 `scripts/build_data.py`와 동일 기조)

### 정적 배포를 위한 파일 분리

GitHub Pages는 서버가 없으므로 집계와 원자료를 나눠 지연 로드한다.

| 파일 | 내용 | 목표 크기 | 로드 시점 |
|---|---|---|---|
| `data/churn-summary.json` | KPI · 일별 추이 · 드라이버 구간 · 세그먼트 · 모델 성능 | < 60KB | 즉시 |
| `data/churn-users.json` | 사용자 5,000명 피처 (배열 기반 + 컬럼 사전) | < 800KB | 타겟 리스트 진입 시 |

- 초기 화면(KPI·추이·원인 진단)은 summary만으로 완성된다
- 사용자 배열은 객체가 아닌 **배열의 배열 + 컬럼명 사전**으로 저장해 키 반복을 제거
- 부동소수점은 소수점 2자리로 반올림

## 7. 기술 스택

기존 `dashboard.html`과 동일한 기조를 유지한다.

| 영역 | 선택 | 이유 |
|---|---|---|
| 호스팅 | GitHub Pages | 고정 요구사항 |
| 프론트엔드 | Vanilla JS + HTML/CSS | 빌드 없이 배포. 규모상 프레임워크 불필요 |
| 차트 | 인라인 SVG 직접 생성 | 외부 CDN 의존 제거 |
| 디자인 | Montage 디자인 토큰 | 기존 `index.html`·`dashboard.html`과 동일 |
| 데이터 생성 | Python 표준 라이브러리 | 의존성 없음 |

### 페이지 구성

- `index.html` — 기존 프로필 (유지), 대시보드 링크 추가
- `dashboard.html` — 아파트 실거래 대시보드 (기존)
- `churn.html` — **본 문서의 대상**

## 8. 비기능 요구사항

- **반응형** — 모바일에서 KPI와 추이 차트는 읽을 수 있어야 함. 타겟 리스트 표는 가로 스크롤
- **접근성** — 위험 등급을 색상만으로 전달하지 않고 텍스트 뱃지(높음/중간/낮음) 병행
- **성능** — 5,000행 필터링·정렬은 클라이언트에서 수행. 표 렌더는 100행으로 제한
- **데이터 출처 명시** — 합성 데이터임을 페이지 상단 배너와 푸터에 **명확히** 표기
- **면책** — 실제 서비스 지표가 아니며 대시보드 설계 검증용임을 명시
